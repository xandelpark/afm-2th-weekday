### 0-5. 크기 맞춰 겹쳐 합치기 — 레이어 방식 (2026-11-04) ← 0-4 의 "잘라 붙이기" 를 대체
- **발견**: 두 카메라 화각이 다르다. 11:53 녹화에서 같은 사람이 A(뒷면 UW)에서 B(앞면 Outer UW)보다 **1.58배** 크다
  (힌지 139° 로 역산하면 짧은 축 화각 뒷면 ≈ 44°, 앞면 ≈ 64°). 그래서 0-4 의 "같은 화각 가정 + 양쪽 12.5% 자르기" 로는
  가운데 사람이 두 번, 다른 크기로 나왔다(사용자 보고 — 폰에서 만든 합본 3840×3412).
- **사용자 요청 그대로 구현**: 저장은 원본 A·B 그대로 두고, 합칠 때 B 를 배율만큼 키워 크기를 맞추고,
  겹친 곳은 레이어처럼 한 영상(기본 A — 더 촘촘한 쪽)을 위에 올린다. 위 영상이 덮은 곳의 아래 영상 사람·물건은 안 보인다.
  이음매 = 위 영상 안쪽 끝 = 이 거치에서는 네트 자리. 이음매만 폭 0.5% 섞어(색 경계 숨김) 나머지는 칼같이.
- 코드 `App/Stitch.swift` 하나에 다 있다:
  - `StitchAlign` (scale, x, y, top, seam, gain, score) — A 화면 좌표 기준. `StitchLayout` 이 픽셀 자리·결과 화면(가로=합집합, 세로=교집합)을 푼다.
  - `Stitch.compose` (Core Image) — 다시 보기와 합본이 같은 함수. 많이 줄일 땐 란초스(그물망 물결무늬 방지).
  - `StitchCompositor`/`StitchInstruction` — AVVideoCompositing. 다시 보기는 A·B 를 한 AVComposition 에 올려 **플레이어 하나**로 돌린다(프레임 단위로 붙어 감).
  - `StitchAligner` — **자동 맞춤**. Vision 정합(VNHomographic/Translational)은 이 쌍에서 엉뚱한 값을 냄(배율 1.5배·겹침 20%는 범위 밖) → 직접 구현:
    윤곽(밝기 기울기) 그림을 폭 64 로 줄여 배율 0.4~2.5 × 좌우 × 위아래 전수 비교(정규화 상관) → 128 → 256 → 512 로 다듬기.
    **256·512 단계는 이음매 근처 띠(폭 12%)만 비교** — 두 카메라가 40° 틀어져 있어 겹친 띠 양 끝의 크기 비가 20% 가까이 달라 한 배율로 다 안 맞는다. 이음매만 맞으면 된다.
    영상 30%·70% 두 시각에서 따로 찾아 답이 같으면(배율 3%·x 1.5%·y 2.5% 이내) 믿는다. 믿을 만한 배율은 `camScale` 로 기억해 다음 녹화는 그 ±3%(역수 포함)만 찾는다.
    색: 겹친 띠의 같은 자리 픽셀 밝기 비율 **중앙값**(선형) — 평균은 카메라 바로 앞 물건(시차)에 끌려가 B 를 20% 어둡게 했었다.
  - `StitchPrefs` — 폴더의 `보기설정.json` {merge, align, auto}. `resolve` = 저장값 → 자동 맞춤 → 나란히. 세로 영상(V자)일 때만 겹쳐 맞춤.
- 실측 결과 (11:53 녹화): B ×1.578, x 0.637, 두 시각 일치. 맥 2.5초 / 시뮬레이터 6초(앱 실행 포함). 이음매에서 벽 윗선 단차 ≈ 화면 높이 1%.

### 0-4. 겹침 자르기 · 사진 앱 저장 (2026-11-03)
- 코트 옆 V자 거치에서는 두 카메라가 네트 쪽을 같이 보므로 가운데가 겹친다. `App/Seam.swift` 가 힌지 각도 θ 와
  (힌지에 수직인 축) 화각으로 잘라낼 비율을 낸다: aMid=(180−θ)/2, aEdge=화각/2, crop=(tan aEdge − tan aMid)/(2 tan aEdge).
  16:9 영상의 짧은 축 화각은 장축 화각(`activeFormat.videoFieldOfView`)에서 `Seam.acrossFOV` 로 환산 (108° → 75.8°).
  → 75.8° 기준 힌지 104° 이하면 겹침 0, 110° 5%, 120° 13%, 130° 20%. **실기기 화각은 진단 로그 "화각 — 뒷면 …" 줄로 확인할 것.**
- 녹화 화면: `DualPreviewHalf(innerIsRight:crop:)` 가 프리뷰 레이어에 아핀 변환을 걸어 안쪽 가장자리를 숨긴다 (V자 거치 + 설정 seamOn 일 때만).
  힌지 알약에 "겹침 N% 잘림" 표시.
- 기록: `MatchLog.hingeDegrees / mount / fovAcross(A,B)` 를 녹화 시작 시점 값으로 저장.
- (0-5 로 대체됨) 다시 보기: `PlayerView.stitched` 가 AVPlayerLayer(.resize) 두 개를 비율 맞춰 붙이고 안쪽을 잘라 한 장면처럼 보인다.
  "겹침" 슬라이더(0~40%)로 손볼 수 있고 폴더의 `보기설정.json` 에 저장. 기록된 각도가 있으면 "N° 기준" 버튼으로 복귀.
  검증: 시뮬레이터에 1800px 파노라마를 A=[0,1080], B=[720,1800] 로 자른 가짜 영상(겹침 33%)을 넣고 hinge 120/fov 81.8 로 17% 자동값 → 이음새 일치 (screenshots/13_player_seam.png).
- 사진 앱: `App/PhotosExport.swift`, 추가 전용 권한(NSPhotoLibraryAddUsageDescription). 녹화 종료 시 자동(설정 saveToPhotos, 기본 켬),
  경기 기록 길게 눌러 수동. 폴더에 `사진앱.txt` 표식. 복사본이라 용량 2배.
- (0-5 로 대체됨) **합본 내보내기** `App/Stitch.swift` + `App/StitchSheet.swift`: AVMutableComposition 에 A·B 트랙, `setCropRectangle`(원본 좌표 — 화면 좌표의 남길 영역을 preferredTransform 역변환) + 변환으로 옆에 붙여 `합본.mov` 로 씀. 소리는 A 만. 크기 원본/절반. 진행률은 `states(updateInterval:)`.
  `Recording.merged` 로 분리(코트A/B 목록에서 제외), 공유는 합본 우선. 검증: 시뮬레이터 `-demo-screen stitch` → 898×960 HEVC, 이음새 일치 (screenshots/14_stitched_frame.png).
- **삼각대 받침** `tools/mount_stl.py` → `mount/` (STL 7개, .scad, 도면). 맥세이프 삼각대는 한쪽 반만 잡아 무거운 쪽으로 기운다는 사용자 보고(2026-11-03)에서 출발.
  치수: 펼친 두께 5.2, 반쪽 폭 82.3, 긴 변 117.8 (GSMArena/9to5Mac). 홈 6.0 × 깊이 14, 바닥 5, 1/4" 구멍 6.8. STL 은 상자 합집합(겹침) — 정확한 CSG 는 .scad.
- **실측 (2026-11-03 11:53 녹화, 힌지 139°, 설정은 '텐트' 였지만 실제로는 네트 기둥 옆 V자)**: 같은 사람이 A 오른쪽 95%, B 왼쪽 20% 위치 → 겹침 25% → 한쪽 12.5%.
  역산한 짧은 축 화각 ≈ 53° (`Seam.measuredAcross`). 4K 영상은 손떨림 보정 크롭 때문에 사진 화각(85°)보다 훨씬 좁다.
  **거치 방식 설정 대신 프레임 회전(세로=V자)으로 좌우 자르기 여부를 정한다** (`framesArePortrait`, `Seam.autoCrop`).
  가까운 네트는 시차로 두 번 보인다 — 먼 쪽(선수) 기준으로 맞추는 게 맞다. 두 반쪽의 수평이 어긋나면(삼각대 기울어짐) 위아래 단차가 생긴다 → 다음 과제: 상하 맞춤 슬라이더·수평계.

## 0-2. 2026-11-02 저녁 — 양쪽 동시 녹화가 실기기에서 된다

사용자 결정: **이 앱의 본체는 앞·뒤 카메라 동시 녹화**이고, **기본 배치는 네트 가운데**(§2 에서 버렸던 그 자리.
사용자가 공 맞는 위험을 알고 택했다). 코트 옆 V 자는 보조 옵션(`Mount.sideV`).

실기기(듀오)에서 확인된 것:
- `AVCaptureMultiCamSession` 에 뒷면 울트라와이드 + 앞면 바깥 카메라, **4K×2 · 30fps**, 양쪽 파일 모두 마이크 소리 들어감.
- 파일: `코트A.mov`(왼쪽 화면 카메라) / `코트B.mov`. 포인트기록에 두 파일 이름이 적힌다.
- 힌지 각도 실시간(`UIHingeInteraction`), 상단에 표시, 거치 방식별 권장 범위 밖이면 주황 배너.
- 회전: iOS `RotationCoordinator` 가 카메라마다 '바로 서는' 각도를 준다. **녹화는 프리뷰와 같은 각도를 쓴다**
  — 중력 기준 '녹화용' 각도를 쓰면 폰을 눕혔을 때 화면과 90° 어긋나게 찍힌다(실제로 그렇게 찍혔다).
- 좌우 배정: 책처럼 펼쳐 안쪽 화면을 볼 때 뒷면 카메라가 오른쪽 반에 있다 → 기본 왼쪽=앞면. ⇄ 버튼으로 바꾼다.
- 검증 방법: `devicectl device process launch ... -- -autorecord 10` 으로 녹화를 돌리고
  `devicectl device copy from` 으로 파일을 꺼내 `ffprobe` 로 본다. 화면은 `devicectl device capture screenshot --display-unique-id 123-456-789`(안쪽) / `987-654-321`(바깥).
- 아직 안 본 것: 네트에 실제로 세운 상태에서 프리뷰와 파일 방향 일치, 텐트 자세에서 회전 좌표가 두 반쪽을 제대로 구분하는지, 두 시간 발열·배터리.

## 2. 버린 설계 — 다시 가지 말 것

처음에는 **폴더블 폰을 역V로 접어 네트 중앙에 거치**하고 앞·뒤 카메라로
양쪽을 동시 녹화하는 구조로 만들었다. `AVCaptureMultiCamSession` 기반 463줄.
**전부 버렸다.** 이유:

| 문제 | |
|---|---|
| **네트 중앙은 공 맞는 자리** | 사용자: "맞을까봐 테니스를 못 친다" — 이것만으로 끝난 설계 |
| 두 `AVCaptureMovieFileOutput` 동시 사용 가능 여부 불명 | 실기기로만 확인 가능 |
| 울트라와이드+전면 조합이 기기에서 열려 있는지 불명 | 기기마다 다름 |
| `hardwareCost ≤ 1.0` 예산 | 듀얼 1080p 는 많은 기기에서 초과 |
| 앞 카메라가 둘 (외부 화면 / 내부 언더디스플레이) | 잘못 집으면 캄캄한 화면이 녹화됨 |
| 접힌 폰을 잡을 거치대가 없음 | 3D 프린트가 필요했음 |

**측면 단일 카메라로 바꾸자 이 6개가 전부 사라졌다.** 거치는 일반 폰 클램프로 되고
화질도 48MP 단일이라 더 좋다. 코드는 463줄 → 334줄.

남은 유일한 화질 차이는 **가까운 코트 vs 먼 코트 약 2.5배** (§3). 그건 사용자가
처음부터 감안한 부분이다.

## 3. 검증된 숫자 — 다시 계산하지 말 것

### 렌즈와 거리

```
울트라와이드 13 mm 환산 → 가로 108.3°  세로 85.4°  (대각 118°)
  ※ 애플 표기 "120°" 는 대각이다. 계산은 가로로 한다.
메인 26 mm → 가로 69.4°
```

| 코트 전체 23.77 m 를 담는 최소 거리 | |
|---|---|
| 울트라와이드 | **8.58 m** |
| 메인 26 mm | 17.17 m — 클럽 코트에선 불가 |

ITF 권장 코트의 측면 펜스 = 중앙선에서 **9.14 m** → 울트라와이드로 **0.56 m 여유**.
9.15 m 에서 가로 25.34 m 가 들어와 베이스라인 밖 여백 0.78 m.

### 선수가 화면에서 차지하는 높이 (키 1.75 m · 4K 세로 2160 px)

| 위치 | 카메라까지 | 화면에서 |
|---|---|---|
| 가까운 쪽 네트 앞 | 9.4 m | 270 px |
| 가까운 쪽 베이스라인 | 15.0 m | 169 px |
| 먼 쪽 네트 앞 | 20.2 m | 125 px |
| 먼 쪽 베이스라인 | 23.4 m | 108 px |

4K 로 찍으면 좌우 반씩 잘라 **코트당 1920×2160**.

### 용량·배터리

| 해상도 | 2시간 |
|---|---|
| 4K | 17.6 GB |
| 1080p | 10.0 GB |
| 720p | 6.4 GB |

배터리 2시간 약 **72%**. 보조배터리를 달면 발열이 올라가 과열 중단 위험이 커진다 —
실제로 상충한다. 한 경기 찍어봐야 결론이 난다.

### 쓰지 않는 배치

- **네트 중앙**: 공 맞는 자리. 그리고 네트에서 4 m 안쪽은 복식 사이드라인이 잘린다.
- **네트 위에서 양쪽을 위아래로**: 양쪽 베이스라인까지 담으려면 **높이 8.58 m** 필요. 불가.

## 6. Xcode 프로젝트 만들기

> **2026-11-02 부터는 손으로 안 만든다.** `project.yml` 이 원본이고 `xcodegen generate`
> 가 `Yangmyeon.xcodeproj` 를 만든다 (xcodeproj 는 git 에 안 넣는다). 아래 수동 단계는
> 전부 `project.yml` + `App/Info.plist` 에 들어가 있다 — 권한 문구, 가로 고정, 파일 공유,
> `MatchCore` 를 로컬 SwiftPM 패키지로 연결(그래서 `import MatchCore` 를 지울 필요가 없다).
>
> ```bash
> brew install xcodegen            # 한 번만
> cd yangmyeon && xcodegen generate
> # 시뮬레이터 빌드 (서명 불필요)
> xcodebuild -project Yangmyeon.xcodeproj -scheme Yangmyeon \
>   -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build
> # 시뮬레이터에서 화면 보기 — 카메라 대신 가짜 코트가 깔린다 (simulator 빌드에만 있는 코드)
> #   실행 인자:  -demo NNNNFFFF   (N=A 득점, F=B 득점)   -demo-record   -demo-broadcast
> #              -demo-sheet setup|log|preflight
> ```
>
> 실기기는 **Xcode 를 열어 Settings → Accounts 에 Apple ID 를 넣고**, `project.yml` 의
> `DEVELOPMENT_TEAM` 에 팀 ID 를 적은 뒤 `xcodegen generate` → 아이폰 연결 → 실행.
> 무료 계정은 7일마다 재서명. 아이폰 쪽은 설정 → 개인정보 보호 및 보안 → 개발자 모드 켜기.

### (참고) 원래의 수동 단계

### 전제: macOS 버전 확인

**Xcode 27 은 macOS Tahoe 26.6 이상을 요구한다.** (Apple silicon 전용)
iOS 27 SDK 는 Xcode 27 에만 들어 있어서 다른 선택지가 없다.

```bash
sw_vers                     # 26.6 미만이면 먼저 OS 업데이트
softwareupdate -l           # 가능한 업데이트 확인
```

필요 공간: macOS 업데이트 7.6 GB + Xcode 약 40 GB.

### 단계

1. **File → New → Project → iOS → App** · Interface **SwiftUI** · Language **Swift**
2. 생성된 `ContentView.swift` 와 `...App.swift` 를 **지운다**
3. `App/` 의 9개 파일과 `Sources/MatchCore/` 의 2개 파일을 끌어다 넣는다
   (Copy items if needed 체크)
4. **`import MatchCore` 를 지운다** — 파일을 직접 넣었으니 같은 모듈이다
   (`ContentView.swift`, `MatchLog.swift`, `Sheets.swift` 세 곳)
5. **Info.plist 에 두 줄 추가.** 없으면 실행 즉시 죽는다.

   | 키 | 값 |
   |---|---|
   | `NSCameraUsageDescription` | 코트를 촬영합니다. |
   | `NSMicrophoneUsageDescription` | 경기 소리를 함께 녹음합니다. |

6. **가로 전용 고정.** Target → General → Supported Orientations 에서
   **Landscape Left/Right 만** 체크. 코트가 가로로 길어서 세로로 쓸 일이 없다.
7. Signing & Capabilities 에서 Apple ID 로 팀 선택 (무료 계정 가능, 7일마다 재서명)
8. **실기기 연결해 실행.** 시뮬레이터에서는 카메라가 동작하지 않는다.

### 첫 빌드에서 막힐 것 — 이름이 틀렸을 수 있는 API

iOS SDK 없이 썼다. Xcode 가 **에러로 정확히 어디가 틀렸는지 알려준다.**
전부 한 줄짜리 수정이고 구조는 안 바뀐다.

| 심볼 | 파일 | 근거 수준 |
|---|---|---|
| `conn.isVideoRotationAngleSupported` / `videoRotationAngle` | CaptureEngine | iOS 17+ 신 API. 구버전 경로를 같이 둠 |
| `AVErrorRecordingSuccessfullyFinishedKey` | CaptureEngine | 불확실 — 없으면 그 한 줄만 지우면 된다 |
| `AVError.mediaServicesWereReset` | CaptureEngine | 확실한 편 |
| `output.minFreeDiskSpaceLimit` | CaptureEngine | 확실한 편 |
| `volumeAvailableCapacityForImportantUsageKey` | Preflight | 확실한 편 |
| `.persistentSystemOverlays(.hidden)` | ContentView | iOS 16+ |

단일 카메라 세션(`AVCaptureSession` + `AVCaptureDeviceInput` +
`AVCaptureMovieFileOutput` + `AVCaptureVideoPreviewLayer`)은 표준 경로라
멀티캠 때보다 틀릴 여지가 훨씬 적다.

### 나머지 미지수

- **4K 가 울트라와이드에서 되나** — `canSetSessionPreset` 으로 물어보고 안 되면
